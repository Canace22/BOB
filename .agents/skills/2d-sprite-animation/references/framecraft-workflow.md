# Framecraft 平台工作流

用于已有序列帧或动作视频的整理与验收。默认使用用户 fork：https://github.com/Canace22/sprite-workbench 。原始上游：https://github.com/EanoJiang/sprite-workbench （仅作来源与按需同步参考）。平台没有静态角色动作生成或运动补间功能，Real-ESRGAN 的“平滑”是图像增强。

## 找到并启动平台

先检查当前项目及已知本地安装，不重复克隆或覆盖工程。使用前确认目录、Git 版本及服务身份；迁移或新安装时读当前 README 和依赖文件，不照搬试用环境版本。工作台是独立工具，本 Skill 不包含其程序或模型。

- 生产构建由 `python -m backend.app` 提供，默认 `127.0.0.1:8765`；开发前端通常为 `127.0.0.1:5173`。检查 `/api/health`，并区分基础接口可用与 AI 模型已加载。
- 仓库启动脚本偏 Windows。Mac 先检查已有 Python/Node 环境，按实际功能安装兼容依赖、构建并启动；不运行 Windows 脚本或直接下载 `.exe`。不要为了导入透明 PNG 下载全部 AI 权重。
- 平滑、AI 抠图、XSXB、透明 MOV 分别检查其运行条件；基础导出成功不代表这些模块可用。模型失败不要悄悄替换算法或把未处理帧说成处理结果。
- 优先用可用的浏览器工具操作真实界面；批量重复操作可用浏览器自动化。使用工具生成的实际下载文件验证，不另写算法伪装平台输出。

## 按素材选择处理步骤

1. **保留输入**：复制到试用目录，读来源时间线、FPS、方向、单次/循环、根部与地面线。只选一组短动作先跑通；不默认处理全部素材。
2. **导入**：图片序列使用零补齐文件名确保排序。导入生成图集前先验证每格布局，必要时按显式裁切框拆成统一画布。角色视频校准源 FPS 和起止区间，再抽帧；动作参考视频只提供运动依据，不能冒充目标角色产物。
3. **保留节奏**：对于整数 tick 的原时间线，可按 tick 复制持帧并沿用原 FPS。例如仅作说明，5 tick 姿势需要显示 5 个播放帧，而不是 1 帧。任意毫秒时长先选择可表达的时间基准并报告量化误差；超过平台限额时采用支持逐帧时长的路径，不擅自丢帧。XSXB 的时长编辑与回传需实际验证，不能假定普通 PNG 序列保留它。
4. **按需处理**：已透明的序列关闭再次抠图、去水印和无关后处理；仅需要去背景时才选择相应引擎。保持整段公共画布和缩放，不按每帧轮廓重新自动贴底。平台导出时的排列对齐不等于角色根部已注册。
5. **检查与预览**：核对保留帧、排序、行列、FPS 与播放模式，观察最大姿势、透明边缘和关键相位。执行主技能的“角色尺度一致性检查”，用固定显示倍率对比原始帧、处理结果及最终导出；平台缺少参考叠图时补充最小对照图，不假定平台会自动修正角色大小。暂停、逐帧、重播并检查单次末帧或循环接缝。压缩只在有尺寸/体积目标时启用；手绘素材可从软缩放、保真 PNG 开始，与原帧同步比较，锐化/透明清理按画面需要调整。不要把缩小尺寸后的节省称为原分辨率无损压缩。
6. **保存与导出**：保存独立 `.framecraft` 工程，再导出所需 PNG 序列/图集。刷新会载入内置示例；从项目列表重开自己的工程，确认参数和处理结果恢复。GIF 用于便捷预览，它不保留 PNG 的半透明边缘，时长也有量化。

## 导出必须独立核对

下列是 `e5dc689` 在 2026-11-02 实测与源码确认的行为；升级后重新读取实际文件，不把缺陷当作永久规则：

- 预览选择单次后，序列和图集的 `manifest.json` 仍为 `loop: true`。游戏动作应按来源时间线配置，不能直接信任此字段。
- 图集 `pivot` 固定为 `{x: 0.5, y: 1}`，不会自动读取外部时间线的根部坐标。将来源根部/地面线按整段缩放和画布偏移换算；只有目标引擎使用归一化坐标时，才再除以输出画布尺寸。
- `e5dc689` 版本的工程可保存大于 60 的 FPS，但重新打开 100 FPS 工程时，第 07 步压缩对比会限制为 60 FPS；第 05 步文字仍显示 100，不能据此认定两处节奏一致。选择不超过 60 FPS 的时间基准，例如 50 FPS 对应 20 ms 的整数持帧，并在游戏元数据中保留相同逐帧时长。若原时长不能精确表示，记录量化变化，重新复核动作与位移步幅，不能只改 FPS 把动作整体放慢。
- 如需修正导出，保留平台原包，在单独的游戏接入副本中修正循环、时长与锚点，记录差异。只是工具试用时，说明限制即可，不擅自修改正式游戏。
- 核对帧数、顺序、尺寸、总时长、Alpha 和图集 rect。未启用处理时可比较 PNG 原字节；经过 Canvas 编码的图集应比较解码像素，区分 Alpha、可见 RGB 与全透明区域。不要要求不同编码的文件哈希一致。

## 已验证范围与回归场景

巨蟹“双钳重砸”试用验证了：来源时间线展开为 39 帧、24 FPS；原始 PNG 字节保留；图集 Alpha 保留；单次停止、暂停及逐帧；50% 软缩放；工程保存后恢复。39 帧、24 FPS、7×6 布局及 50% 比例都是该样例参数，不是技能默认值。未验证 AI 抠图、Real-ESRGAN、XSXB、视频抽帧与透明 MOV。

用户随后指出巨蟹身体宽度变化。后续以待机壳体为参照，经过两轮图像编辑、整段统一缩放和按固定壳体特征平移注册，保留原持帧节奏和身体下沉。特征匹配估计的横向尺度由原版最大约 +10.3% 改善到候选约 −2.3%～+2.6%；用户观看同步对比后反馈“好多啦”。这支持“身体尺度明显改善”，不代表纹理、肢体、动作或游戏接入全面通过。修正方法、测量限制和分辨率代价见 [尺度修正经验](scale-repair.md)。

更新平台流程时优先覆盖这些场景：

1. 只有静态角色：先补真实动作，不能通过复制/缩放得到“新动画”。
2. 已有不等时长序列：保留姿势停留与总时长，重复持帧不计为新姿势。
3. 透明单次攻击：关闭无关抠图，核对实际导出循环标记和原根部。
4. 缩小素材：帧序、FPS 不变，坐标按公共变换换算，体积收益和细节损失分别报告。
5. 保存后重开或平台不可用：前者确认工程恢复，后者说明缺口并用最小替代路径继续，不声称未经执行的功能通过。
