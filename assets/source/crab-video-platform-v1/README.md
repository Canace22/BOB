# 原视频九组巨蟹动作：Framecraft 压缩整理

2026-11-02，把之前视频拆出的 **9 组、360 帧**通过 Framecraft 实际压缩 API、PNG 导出和工程保存/重开处理了一遍。来源帧不覆盖，帧序、12 FPS 和原片 0–30 秒的动作区间不变。

整段按 75% 等比缩小：**896×512 → 672×384**，公共根部 **(512,448) → (384,336)**。使用 soft/Lanczos、RGBA PNG、锐化 20、透明阈值 2，不做调色板量化。360 张 PNG 总量从 **57,514,629 B** 减至 **34,575,979 B**，减少 **39.88%**；这是缩小和透明边缘整理后的体积收益。

这批没有重绘缺钳、补画被遮挡的身体，也没有生成独立的左右两套。旧抠图缺损、尘埃/前景遮挡和原片转向仍然存在，不能作为最终动画或游戏接入验收通过的证据。

## 在工作台查看

在 Framecraft 顶部选择某个动作目录下的 `projects/`，打开名称为“巨蟹视频_动作名_75%PNG_v1”的工程。第 07 步保存了原图和处理结果的同步比较。各工程的位置及名字见 [批次总表](review/batch-summary.json)。

每个动作目录包含：

- `processed/`：实际 API 返回的 PNG 序列。
- `exports/<动作ID>.zip`：调用平台原导出函数生成的 PNG ZIP，原样保留。
- `projects/`：独立 `.framecraft` 工程，内含原帧和结果；不依赖外层源目录来重开。
- `game-metadata.json`：保留动作单次/循环、帧序、公共画布和根部的接入参考。
- `source-map.json`：本地 PNG 与原视频帧号、时间、原根部及输入/输出 SHA-256 对应。
- `review/`：API 参数、工程重开、实际 ZIP 与透明通道检查。

**平台 PNG 导出的 manifest 总会写 `loop:true`。** 只有待机沿用循环，其余八组必须使用 `game-metadata.json` 的单次标记。不能把平台默认底部中央锚点当成 `(384,336)`。

## 复跑

原来源路径和 `animations.json` 哈希见 [批次总表](review/batch-summary.json)，原时间线副本为 [source-animations.json](source-animations.json)。没有在各动作外层重复复制源帧；工程本身保留制作输入，检查报告另记原始路径及哈希。

入库的清单副本只将CRLF换行统一为LF，所有JSON字段和值保持相同；`sourceManifestSha256`仍对应外部原始文件的字节，不是换行整理后副本的哈希。原文件没有修改。

```sh
node process-all.mjs <Framecraft仓库> <crab_boss_sprites来源目录>
```

脚本复用 [process.mjs](../crab-animation-platform-v1/process.mjs) 与 [verify.py](../crab-animation-platform-v1/verify.py)，不复制平台图像算法、不操作浏览器 UI、不下载模型。平台需已运行于 `127.0.0.1:8765`。每次运行由平台创建新工程；不要将其他动作写入已有动作输出目录。

仅复核现有导出时，`verify.py` 在原始外部目录不可用时自动读取工程内的源帧；也可运行 `python3 ../crab-animation-platform-v1/verify.py <动作目录> --embedded-source`，不依赖原制作机器的绝对路径。重新从视频提取则仍需取得原视频。

本批未导出压缩图集，图集功能依赖浏览器 Canvas；PNG 序列和可重开工程随制作批次本地入库。未改游戏代码、未发布试玩。
